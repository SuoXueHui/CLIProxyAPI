# Findings

- CPA core already passes the selected stable `Auth.ID` into the pure weekly-overdraft transform.
- Controller account rows expose the same identifier as `cpa_auth_id`; grouped rows retain each credential's `cpa_auth_id` in `credentials`.
- The existing Manager page already polls the core endpoint every 15 seconds and renders 5h/7d usage in a compact cell, so account-level status can reuse both paths without a new timer or table column.
- Existing global outcomes cross observe/inject hot changes. New per-auth outcomes must be action-scoped to preserve semantics.
- The account tracker uses `sync.Map` only for auth entry lookup/creation and per-entry atomics for steady-state requests; there is no global request mutex.
- The endpoint accepts repeated `auth-id` filters and returns a deterministic last-seen-descending account array; without filters it returns all active entries.
- Account entries are capped at 8192 and are removed after six hours of inactivity during status snapshots; hitting the cap drops account-only observability without changing the request or global metrics.
- The live CPA and Manager images still point to the earlier global-panel release commits (`6e8229af` and `ef4bbd92` respectively). Publishing the account extension therefore requires replacing only those two images; Controller and its data model remain unchanged.
- Final production evidence aligns global and account counters: `evaluated=22`, `injected=2`, global success=2, two account entries with injected requests, and summed per-account injected success=2. Two visible rows also have 7d official quota at 100%, but the UI correctly labels the CORE data as operational evidence rather than guaranteed extra entitlement.
- A fresh cross-day check after about 14 hours of runtime found 74 active six-hour account entries and 923 account-level injected requests: 540 success, 81 usage-limit, 298 hard-stop, 0 canceled, and 4 other-failure. CPA and Manager both remained restart=0/OOM=false, and the browser console remained clean.
- The author plugin remains enabled and registered at v0.3.1332 for account management, while its `weekly_overdraft_enabled` experiment switch remains false. The active 10%/1-pair injection therefore still comes only from the CPA core implementation.
- The final six-hour log sample contained one unrelated Manager `POST /v0/management/monitoring/analytics` 500 caused by a canceled projection query; the same interval's CORE status requests were 200, so this is recorded as an existing monitoring baseline rather than an account-statistics regression.
- The phase-two 25%/1-pair trial failed its stability gate: after a clean CPA counter restart, 94 requests were evaluated and all 11 injected attempts ended as hard stops with zero success or 429 outcomes. Controller correlation still labeled all tracked accounts active, while CPA logs showed non-retryable OAuth 401 refresh failures on injected and non-injected requests, so increasing pair strength would not address the observed failure mode.
- The production config was restored through the authenticated full-YAML management endpoint to 10%/1 pair without another restart. Host and container config checksums match, the reload log advanced, and the author plugin experiment remains disabled.
- Atomic host replacement of a single-file Docker bind mount changes the host directory entry without updating the mounted inode. Production config changes must therefore use the authenticated in-container management save path; if the paths diverge, synchronize the host file and recreate the container to restore a durable mount relationship.
- The user clarified that the failed 25% window ran before valid accounts were available and explicitly requested holding 25% while accounts are imported. For this pre-import interval, service health and configuration integrity are the rollback gate; outcome quality must be evaluated only after useful account traffic arrives.
- The requested 25% hold is now live without a restart: config reload succeeded on the first poll, all three service health gates pass, and host/container/candidate checksums match. Existing failed outcomes are retained in the process-local counters until CPA restarts and must be separated from the post-import account sample when judging 25%.
- A live request 401 is reproducible as an OAuth refresh failure, not a weekly-overdraft transform failure: CPA logs show `refresh_token_invalidated`, followed by `session-affinity: cache hit but auth unavailable, reselected`, then the same `/v1/responses` request returns 401.
- The current CPA auth pool contains 28 Codex files marked `status=active`; 27 have recent failed requests (6--15 each, all success=0) while one newly imported Team credential (`auth_index` prefix `83a5a083`) has failed=0. Both the failed credential (`cca14850`) and the fresh credential remain marked active after probes, proving status convergence is stale.
- Direct management quota probes distinguish the credentials: fresh `83a5a083...` returns HTTP 200 with a Team seven-day window, while failed `cca14850...` returns HTTP 401. Therefore the valid account exists but is not guaranteed to receive a request while invalid active credentials remain in the selection pool.
- Session affinity only reselects an auth after detecting the cached auth is unavailable; the observed request still terminates with 401 after the reselect, so one valid account does not currently guarantee same-request failover.
- The live timeline disproves 25% as the source of token invalidation: the first `refresh_token_invalidated` refresh failure was logged at 14:21:56, while the `canary-percent: 10 -> 25` hot reload occurred at 14:37:56. Raising the canary increased exposure and made the stale pool easier to hit, but did not revoke the tokens.
- The production Manager policy endpoint reports `authIssueQueue.enabled=false` and `authIssueAutoDisable.enabled=false` (startup defaults). Consequently, Manager does not consume these authentication-failure events for persistent disable; CPA only records runtime `StatusError`/`Unavailable`, leaving `disabled=false`.
- A later read-only auth snapshot shows the invalid credentials in `status=error, unavailable=true, disabled=false`, while the separate quota/plugin automation has disabled other quota-exhausted entries. This confirms runtime quarantine and persistent disable are separate state machines.
- A follow-up read-only check at 15:49 found a run of successful `/v1/responses` requests (HTTP 200), but also two recent 503 responses. The Codex state snapshot still contains five `error + unavailable=true + disabled=false` entries, so recovery is runtime fallback to usable credentials, not persistent invalid-account cleanup.
- The live account route reproduces the screenshot semantics: `kellanbrazile...` has a fresh seven-day snapshot at 1% used / 99% remaining while its account-level CORE strip already reports injected requests. The CPA transform gates on OAuth, eligible request tail, body size, idempotency, and deterministic canary bucket; it does not read official 5h/7d usage before injecting.
- The `35 req`/`25 req` quota-card figures and `CORE 6h 注入` figures are different data paths and scopes. Merged rows can aggregate multiple CPA credentials, while official quota may be fresh/stale or missing; CORE counters are process-local six-hour operational metrics. Their values must not be compared as a quota gate.
- A clean live 25% window starting at `2026-08-16 14:08:33` reached `evaluated=8230 / injected=1348 / success=1128 / usage-limit=104 / hard-stop=105 / canceled=0 / other-failure=10`; one request was still in flight at the snapshot. The effective injected share was 16.4% because 25% is a stable-session canary after request eligibility checks, not a per-request quota.
- The loaded account rows covered all terminal outcomes at the comparison point. Accounts whose latest visible seven-day quota snapshot was 100% contributed 1213 injected requests and 1034 successes (85.2%), so the current success is not explained only by accounts with unused quota. This remains operational correlation because quota snapshots and CORE counters have different clocks and scopes.
- `/v1/responses` improved from 84.8% HTTP 200 since the clean start to 88.8% over the latest hour and 90.4% over the latest 15 minutes. The latest 15 minutes still contained 28 HTTP 503 responses out of 1963 requests (1.4%) and 533 session-affinity reselections after cached credentials became unavailable.
- Service health is stable (`restart=0`, `OOM=false`, CPA/Manager/Controller up, three HTTP health surfaces 200), but the credential pool is still churning. The stability-first decision is therefore to hold 25%/1 pair, not increase to 40% or 50%; reconsider only after credential reselection is reduced and 503 stays below 1% for another representative window.

No panic/fatal/OOM/token-invalidated markers appeared after the 50% switch, and the latest 15-minute Controller/Manager container logs contain no warning/error lines. The regression is request-quality and credential-capacity pressure rather than a service crash.
